# Design

## Context

See `proposal.md` for motivation and `specs/backend/wallet-reconciliation-api/spec.md` for the behavioral contract. The service ingests normalized wallet, provider, and ledger records, persists runs and discrepancies, and exposes current-evidence explanations. Each date/channel pair has a single reconciliation run. The requested automatic closure is intentionally limited to known synthetic demo scenarios at initial run creation; timeout and non-demo discrepancies remain open for manual investigation.

## Goals / Non-Goals

**Goals:**
- Keep reconciliation classification and demo-only status transitions in the backend source of truth.
- Automatically close only known functional discrepancy scenarios generated by the demo seed.
- Put the exact automatic reason in the investigation note when creating a demo discrepancy; these seed-created cases have no prior human note.
- Keep timeout discrepancies open and allow the existing web workflow to collect a human investigation note.
- Ensure resolved discrepancies never transition back to an unresolved state.
- Keep MCP tools from loading data or performing status changes.

**Non-Goals:**
- Add run versioning, a second run for the same date/channel, scheduled reconciliation, or a background worker.
- Auto-resolve non-demo records or timeout scenarios.
- Reopen resolved discrepancies, including when later source evidence conflicts with their resolution.
- Replace the deterministic matcher with an LLM or expose source loading through MCP.

## Decisions

### Apply the demo closure rule while creating the reconciliation

When the backend creates a run from seeded demo records, it classifies the available evidence as it does today and sets `RESOLVED` plus the approved investigation note only for the known synthetic scenarios: QR amount mismatch, missing QR provider result, and P2P provider `PENDING`. A separate seeded provider `TIMEOUT` remains `OPEN`. Other discrepancies and all non-demo references retain the existing manual workflow. Scoping by the established synthetic demo reference convention prevents the closure policy from changing operationally uploaded transactions.

The single-run uniqueness constraint remains unchanged. Auto-resolution is part of the initial run result and does not create another run or alter the original report identity.

### Preserve reconciliation and resolution metrics separately

The transaction with an automatically resolved discrepancy remains part of `transaction_count` and the resolved counters, but not `reconciled_count`; that metric continues to mean no discrepancy was detected in the initial comparison. An open timeout counts as unreconciled until the existing manual workflow resolves it.

### Make resolution terminal
The automatic demo rule assigns the resolution only when the discrepancy is created. It must never change an existing discrepancy; the existing API conflict for manual reopen remains in force.

### Keep MCP as a request/response client
MCP continues to delegate permitted queries and explicit reconciliation requests to the API. It gains no record-loading or discrepancy-writing tool. Demo auto-resolution happens only as part of a user-requested backend reconciliation, not at startup.

### Generate a 14-day synthetic demo window with repeatable timeout cases

Seed the 14 complete calendar days before the current `America/Lima` date idempotently. Include a provider timeout scenario on a small, deterministic subset of those days. Represent the timeout with provider status `TIMEOUT`, classify it as `PROVIDER_NOT_SUCCESSFUL`, and provide the human-readable detail `Tiempo de espera superado`; the web can use its existing manual investigation flow.

## Risks / Trade-offs

- [A demo-only rule could accidentally resolve operational data] → Match only references following the established synthetic seed convention and test that other references of the same discrepancy types remain open.
- [A `TIMEOUT` provider value could be mistaken for an ordinary failure] → Extend request validation and web copy explicitly, while retaining the existing discrepancy type and manual status workflow.
- [Resolved demo cases may be misread as clean reconciliations] → Keep transaction, reconciled, and resolved counters separate and test their reported values.
- [Additional demo days may collide with persisted data] → Keep seeding idempotent and never delete source records or create runs during startup.

## Migration Plan

No destructive migration is required. Extend provider status validation additively and ensure an existing local database can start and seed the additional dates without deleting or rewriting source records, reconciliation runs, discrepancies, or investigation notes. No automatic database reset is permitted.
